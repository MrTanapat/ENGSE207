# การสะท้อนคิด สัปดาห์ที่ 4: Layered Architecture

## 1. สิ่งที่เรียนรู้

จากการทำ Lab สัปดาห์นี้ได้เรียนรู้หลักการ Separation of Concerns อย่างเป็นรูปธรรม กล่าวคือการแบ่งโค้ดออกเป็น 3 ชั้น ได้แก่ Controller, Service และ Repository ทำให้แต่ละส่วนมีหน้าที่ชัดเจนและไม่ก้าวก่ายกัน นอกจากนี้ยังเข้าใจว่า Dependency Flow ควรไหลจากบนลงล่างเสมอ คือ Controller เรียก Service และ Service เรียก Repository เท่านั้น ไม่มีการเรียกย้อนกลับ ซึ่งทำให้ระบบมีโครงสร้างที่คาดเดาได้และดูแลง่าย

## 2. ข้อดีที่พบจากการทำจริง

- หาบั๊กง่ายขึ้นมาก — เมื่อ validation ผิดพลาด รู้ทันทีว่าต้องไปดูที่ taskService.js ไม่ต้องไล่หาในไฟล์เดียวที่มีโค้ดปนกัน
- แก้ไขโค้ดได้อย่างมั่นใจ — เมื่อต้องการเปลี่ยน SQL query ก็แก้เฉพาะ taskRepository.js โดยไม่กังวลว่าจะกระทบ business logic
- อ่านโค้ดเข้าใจง่าย — แต่ละไฟล์มีขนาดเล็กและมีจุดประสงค์เดียว ทำให้เข้าใจได้เร็วกว่า server.js ไฟล์เดียวที่มี 150+ บรรทัด

## 3. ความท้าทายที่พบ

ความท้าทาย 1: ในช่วงแรกสับสนว่า validation ควรอยู่ที่ Controller หรือ Service
วิธีแก้: ใช้หลักการแยกแยะว่า format validation (เช่น ตรวจว่า ID เป็นตัวเลขไหม) อยู่ที่ Controller ส่วน business validation (เช่น title ต้องมีอย่างน้อย 3 ตัวอักษร) อยู่ที่ Service

ความท้าทาย 2: การส่ง error ขึ้นมาผ่าน layers ให้ถูกต้อง
วิธีแก้: ใช้ try-catch ใน Controller และเรียก next(error) เพื่อส่งต่อไปยัง errorHandler middleware แทนการจัดการ error เองในทุกที่

## 4. การจัดโครงสร้างโค้ด

การแบ่ง layers ช่วยให้การจัดโครงสร้างโค้ดดีขึ้นอย่างไรเมื่อเทียบกับสัปดาห์ที่ 3?

เมื่อเทียบกับสัปดาห์ที่ 3 ที่โค้ดทั้งหมดอยู่ใน server.js ไฟล์เดียว การแบ่ง layers ช่วยให้โครงสร้างดีขึ้นในหลายด้าน
ใน Monolithic เมื่อต้องการเพิ่มฟีเจอร์ใหม่ต้องเลื่อนหาตำแหน่งที่ถูกต้องในไฟล์ใหญ่ แต่ใน Layered รู้ทันทีว่าต้องไปเพิ่มที่ไหน เช่น กฎใหม่ทางธุรกิจไปที่ Service, SQL ใหม่ไปที่ Repository และ endpoint ใหม่ไปที่ Controller นอกจากนี้การทำงานเป็นทีมก็ง่ายขึ้น เพราะสมาชิกแต่ละคนสามารถรับผิดชอบคนละ layer ได้โดยไม่ conflict กัน

## 5. เมื่อไหร่ควรใช้ Layered Architecture

Layered Architecture เหมาะสมในสถานการณ์ต่อไปนี้
- ทีมมีขนาด 3 คนขึ้นไป ที่ต้องทำงานพร้อมกัน เพราะการแบ่ง layer ช่วยลด conflict ในการแก้โค้ด
- โปรเจกต์ที่ต้องดูแลระยะยาว เช่น ระบบที่ใช้งานจริงในองค์กร ที่มีการเพิ่มฟีเจอร์และแก้บั๊กอยู่เสมอ
- ระบบที่มี business logic ซับซ้อน เช่น ระบบธนาคาร ระบบโรงพยาบาล ที่มีกฎทางธุรกิจจำนวนมาก
- เมื่อมีแผนจะเปลี่ยน database หรือ framework ในอนาคต เพราะ Layered ช่วยให้เปลี่ยนได้โดยกระทบส่วนอื่นน้อยที่สุด

## 6. การวิเคราะห์ Trade-offs

### ข้อดี
- แต่ละ layer มีหน้าที่ชัดเจน ทำให้โค้ดอ่านและเข้าใจง่าย
- แก้ไขส่วนใดส่วนหนึ่งโดยไม่กระทบ layer อื่น
- ทดสอบแต่ละ layer แยกกันได้อิสระ
- รองรับการทำงานเป็นทีมได้ดี
- เปลี่ยน technology ใน layer ใดก็ได้โดยไม่กระทบทั้งระบบ

### ข้อเสีย
-จำนวนไฟล์เพิ่มขึ้นมากเมื่อเทียบกับ Monolithic
- มี boilerplate code ที่ต้องเขียนเพิ่ม เช่น การส่ง error ขึ้นผ่านทุก layer
- มี performance overhead เล็กน้อยจากการเรียกผ่านหลาย layers
- อาจ over-engineering สำหรับโปรเจกต์ขนาดเล็ก

### การประเมินโดยรวม
Layered Architecture คุ้มค่ากับความซับซ้อนที่เพิ่มขึ้น สำหรับโปรเจกต์ที่มีขนาดกลางถึงใหญ่และต้องการความยั่งยืนในระยะยาว ความยากในช่วงเริ่มต้นที่ต้องออกแบบโครงสร้างนั้นได้ผลตอบแทนคืนมาในรูปแบบของการดูแลและขยายระบบที่ง่ายขึ้นอย่างมีนัยสำคัญ อย่างไรก็ตามสำหรับ prototype หรืองาน hackathon การใช้ Monolithic ยังคงเป็นตัวเลือกที่เหมาะสมกว่า
